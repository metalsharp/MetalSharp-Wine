## Call of Duty 4's videos play, City of Heroes' blend factors, and image atomics on the M6

WineMetalGL 4.1.0 fixes videos that a game decodes on a thread of its own, which came out pink in Call of Duty 4, answers two blend-state queries that City of Heroes makes as it starts, and works around a Metal bug with image atomics on the M6.

### Videos decoded on a thread of their own ([MetalSharp-Wine#58](https://github.com/metalsharp/MetalSharp-Wine/issues/58))

- **The bug:** Call of Duty 4's Bink videos were solid pink. Bink's thread copies each frame's Y, U and V planes into textures, and the render thread draws with them. WineD3D gives each thread its own GL context and flushes a context only when its thread switches to another, so Bink's thread never flushed. WineMetalGL sends a context's uploads to the GPU only when that context's work is committed, so the uploads never reached the GPU, and the render thread never saw them.
- **The fix:** while other contexts of the share group are current, a texture upload made outside a render pass is now sent to the GPU at once. An upload during a pass still goes with that thread's next commit, so passes aren't broken up, and a single context works as before.
- A D3D9 program doing what the game does read 0 for every value before and reads them all now, as a 32-bit and a 64-bit program, with WineD3D's CSMT on and off. Call of Duty 4 itself hasn't been tested yet.

### City of Heroes' blend factors ([#94](https://github.com/metalsharp/WineMetalGL/issues/94))

- `GL_BLEND_SRC` and `GL_BLEND_DST`, OpenGL 1.x's names for the blend factors, are now answered in compatibility contexts, where City of Heroes' renderer got `GL_INVALID_ENUM`.
- **Not fixed yet:** City of Heroes still may not offer all of its graphics options, bloom among them. What hides them isn't known yet, so #94 stays open.

### Image atomics on the M6 ([#98](https://github.com/metalsharp/WineMetalGL/pull/98))

- **The bug:** on the M6 (macOS 27.3), a shader that changes a texel of an image atomically and then reads it back got the value from before the change, though GL requires it to see its own change. This is a Metal bug: a plain Metal shader doing only that read the old value for 81,900 of 81,920 texels, fences and all.
- **The workaround:** an image a shader uses atomics on is now read with Metal's atomic load, which returns the right value. Shaders without image atomics are unchanged.
